# KPL 2K 产品 PRD（v0.1 草案）

> 状态：规划中，待拍板
> 日期：2026-08-15
> 一句话定位：一款"战队经理"式的 KPL 赛季模拟网页游戏——自由搭配任何年代的选手（或整编老战队阵容），在任意年份的 KPL 赛场上模拟一个赛季，看能不能夺冠。

---

## 1. 背景与目标

### 1.1 要解决的问题

市场上有 BP/版本 meta 类的电竞模拟产品，但没有"跨年份自由组队 + 宏观赛季模拟"的产品。用户想要的不是局内操作，而是：

- 选人、换人，组出心目中的最强战队或整活阵容；
- 用老战队阵容（如 2017 QGhappy、2019 eStarPro）在任意年份征战；
- 比赛只是宏观结果（"AG 4:2 狼队"），核心乐趣在"这个阵容到底能不能夺冠"、"会不会翻车/爆冷"。

### 1.2 最终形态要求（用户明确）

1. **手机优先**：手机浏览器（微信内置浏览器、Safari/Chrome 等）打开顺畅，首屏秒开，交互流畅。
2. **可传播**：低摩擦分享——无登录、无下载、链接即玩；结算生成可保存/转发的战绩图；好友可点链接直接对战/复现阵容。
3. **可持续迭代**：新赛季发布后能低成本更新数据；平衡参数可调；前端可增量升级，不破坏已有内容。

### 1.3 完成标准（总）

- 手机 4G 网络下，分享链接打开 < 3 秒可玩；
- 无登录、无下载，一个链接完成"打开 → 组队 → 模拟 → 分享"；
- 数据、模拟参数、UI 文案三层解耦，任何一层都能独立更新。

---

## 2. 用户与核心场景

### 2.1 目标用户

- KPL 核心观众 / 王者荣耀玩家（主力）；
- 老 KPL 粉丝（情怀：梦泪、老帅、Cat、Fly、久诚……）；
- "整活"型玩家（组奇怪阵容看翻车）；
- 轻度云玩家（刷到分享图点进来玩一把）。

### 2.2 核心场景

1. 刷到朋友分享的"我的阵容夺冠了"战绩图 → 点链接 → 玩一把 → 也生成一张战绩图。
2. 老粉丝想验证"2019 eStarPro 五虎放到 2024 能不能夺冠"。
3. 整活：全明星选手 + 三名不知名选手，看会不会爆冷。
4. 每年新赛季开赛前，用"上赛季阵容"模拟预测。

## 3. 核心玩法循环

```
选择模式（经典 / 全明星）→ 组队 → 挑选战场（年份/赛事）→ 看预测 → 模拟整个赛季
  → 赛程比分 + 冠军 + 亮点事件（爆冷/翻盘/黑马）→ 结算 → 生成战绩图分享
```

### 3.1 双模式（核心差异）

- **经典模式（现实向）**：选定一支战队后，只能在该战队旗下选人，不能跨战队；但允许跨时期——例如 2019 年的 Fly 和 2026 年的信（同属狼队）可以同队，组出"狼队历代最佳阵容"。选定战场后，你替代该赛季中这支战队的位置，与当年的真实联盟对战（固定战队打固定阵容）。
- **全明星模式（整活向）**：不受战队限制，从全历史选手池任意挑选 5 人组队，回答"关公战秦琼"。细节后置（MVP 先只做经典模式）。

### 3.2 玩法细节（按流程顺序）

- **组队（先）**：开局列出当前（2026）全部 KPL 战队，玩家选队后初始阵容自动为该队 2026 首发；之后可在该队全历史选手池任意调换（5 名首发，允许多位置选手）；可保存到本地。选手以"版本卡"呈现：同一选手按赛季/位置拆分为多张卡（如 2023·小胖·打野、2021·无畏·打野），战力 = 当季评分（0–100）；位置切换版本由人工校对覆盖表修正（试点：无畏 2020–2022 打野 / 2023 起辅助）。
- **轮换（系列赛间隙）**：首发 5 人 + 替补席（MVP 建议 2–3 人）；每个系列赛结束后可换人（默认理解：无论输赢都可调整，换人影响后续强度与叙事；若只想"赢了才能换"，改一行配置）。
- **挑选战场（后）**：年份 + 赛事类型（KPL 春季赛/夏季赛/秋季赛、挑战者杯等），MVP 先做 3–5 个代表性赛季。战场决定对手阵容、赛制与强度。
- **预测（可选）**：给出夺冠概率、阵容短板、预测排名区间，让"爆冷"可感知。
- **模拟**：一键模拟整个赛季（常规赛 → 季后赛 → 决赛），输出：
  - 每轮赛果：系列赛比分（如 "AG 4:2 狼队"）、关键战（爆冷/翻盘/黑马）；
  - 赛季数据：常规赛排名、季后赛晋级路径、冠军、FMVP 候选人；
  - **小局战报**：每个系列赛内每小局输出一段文字解说——开局（换边/体系克制）→ 事件（龙团/抢龙/团战）→ 终结（平推/翻盘）→ 当前比分；事件槽位由模拟结果填充（谁抢龙、谁 MVP），模板片段可自由组合，如 "双方换边，红方狼队用一套盾曹体系克制蓝方AG的戈雅……十分钟龙团狼队.小胖抢到暴君……狼队平推水晶，目前比分狼队 2:1 AG"。
- **结算与分享**：生成战绩卡（长图）+ 可分享链接（URL 携带阵容与结果）。

### 3.3 明确不做（MVP）

- 不做 BP、英雄、版本 meta、局内操作；
- 不做养成、卡牌抽奖、付费；
- 不做账号系统/服务器排行榜（MVP 阶段）。
- 不做 2016–2018 赛季数据（已拍板：从 2019 开始）。

## 4. 数据资产（已探明，实测确认）

### 4.1 数据源

| 源 | 内容 | 覆盖 | 状态 |
|---|---|---|---|
| kpl.qq.com 官网接口 | 赛季列表、战队、赛程比分、战队荣誉/口号/赛季数据 | 2016–2026 全部 23 季 | ✅ 已验证可爬 |
| prod.comp.smoba.qq.com（pvp.qq.com/matchdata 后端） | 选手赛季数据、战队赛季数据、赛程+逐局结果、逐局首发阵容（选手+英雄+MVP） | 2019–2026 共 32 个赛事 | ✅ 已验证可爬 |
| 人工种子数据 | 2016–2018 三季选手/阵容 | 3 季 | ⚠️ 待拍板（可做可不做） |

### 4.2 关键数据字段（实测）

- 选手：选手名（ID）、位置、战队、KDA、场均击杀/助攻/死亡、胜率、场次、场均经济、分均伤害、分均承伤、MVP 数据。
- 比赛：对阵双方、系列赛比分、BO、阶段、日期、每小局 battle_id。
- 小局：双方阵容（选手名+英雄）、MVP、击杀/经济/伤害、时长。
- 战队：赛季胜率、战绩、荣誉墙（冠军/亚军/季军/四强列表）、口号。

### 4.3 数据规模估算

- 选手-赛季记录：约 2,500 条（2019–2026，每赛事 70–120 人）；
- 比赛记录：约 6,000 场；逐局 battle 约 3 万局（只提取聚合并丢弃原始快照）；
- 精简后数据包：< 3 MB（gzip 后 < 2 MB），按赛季分片，手机可接受。

### 4.4 已知数据坑（爬虫必须处理）

1. **战队/选手名为当前名**：2019 的 QGhappy 显示为"重庆狼队"；历史归属需用 kpl.qq.com 的赛季战队表 + 逐局阵容反推。
2. **小局 win_camp 阵营顺序会翻转**：以每局实际 `is_win` + 队名为准，不能直接累加。
3. **位置字段可能是当前值**：历史赛季位置以逐局首发为准。
4. 2016–2018 选手数据官方已清理（接口返回 404），只能人工补齐。

## 5. 传播设计

### 5.1 传播链路

1. **战绩图**：canvas 生成 1080px 长图（阵容 + 赛季 + 冠军 + 一句话战报），微信内长按保存/转发；
2. **可分享链接**：URL 参数携带阵容与年份（如 `?y=2021&p=1001,1005,...`），打开即还原；
3. **好友对战/对比**：链接对比两人的阵容与战绩（纯前端，不依赖服务器）。

### 5.2 低摩擦原则

- 无登录、无下载、无弹窗；
- 首屏即"选择年份"或"一键体验"按钮，3 步内出结果；
- 数据按需加载：默认只加载第一个可用赛季。

### 5.3 传播钩子（内容层面）

- 情怀：老阵容一键体验（"2017 QGhappy 王朝"等）；
- 整活：奇怪阵容分享率天然高；
- 争议性：选手评分是民间版，可引发"凭什么 Fly 比 XX 低"的讨论；
- 赛季预测：每年开赛前可玩"卫冕冠军能不能连冠"。

## 6. 技术架构

### 6.1 总体形态

**纯静态单页应用（无后端）**：

```
数据管线（本地工具，Python）
  ├─ 爬虫：kpl.qq.com + prod.comp.smoba.qq.com
  ├─ 清洗/校验：赛季-选手-比赛关联、当前名修正、比分一致性检查
  └─ 产出：data/players.json、data/seasons.json、data/matches.json（按赛季分片，gzip）
          ↓
静态站点（HTML + CSS + JS + data/）
  ├─ 移动优先 UI（组队 → 模拟 → 结算 → 分享）
  ├─ 模拟引擎（纯前端 JS，纯函数）
  ├─ 叙事模板（数据驱动战报）
  └─ 战绩卡生成（canvas）
          ↓
静态托管（GitHub Pages / COS+CDN / 其他）
```

### 6.2 技术选型原则

- **零构建优先**：MVP 用原生 JS + 按需加载 JSON 分片，避免构建链拖慢迭代；如 UI 复杂度上来再引入轻量框架。
- **纯函数引擎**：模拟器与 DOM 完全解耦，可单元测试、可复现（seed 随机数）。
- **数据驱动**：选手、赛季、平衡参数全部 JSON 配置化；新增赛季 = 跑数据管线 + 加一个 JSON 分片。
- **性能预算**：首屏 JS+CSS < 300 KB（gzip）；单赛季模拟计算 < 50 ms；数据分片懒加载。

### 6.3 数据管线（本地工具）

- 脚本：`crawl_*.py`（拉取）→ `clean_*.py`（清洗、关联、校验）→ `build_json.py`（输出前端数据包）；
- 校验门禁：随机抽 N 场比赛与官方比分交叉核对；冠军/决赛比分一致性 ≥ 95% 才允许发布数据；
- 更新流程：新赛季结束后重跑 → 生成新版本数据分片 → 更新 `data/index.json`。
- 赛制提取：从官方赛程数据自动重建每赛季结构（分组/轮次/晋级树）→ `formats.json`；引擎按配置模拟，天然对齐真实赛制，无需手写各赛季赛制。

### 6.4 迭代机制

- 三层解耦：**数据**（可重爬）、**平衡参数**（config.json：爆冷系数、评分权重、化学加成）、**UI/文案**（独立文件）；
- 数据带版本号，前端旧链接不回退；
- 平衡调整通过模拟 1000 次分布验证后发布。

### 6.5 为什么不需要后端（MVP）

- **模拟在用户手机浏览器里运行**：引擎是纯函数，输入"阵容 + 战场 + 随机种子"输出整个赛季，不需要服务器计算。
- **选手数据是打包好的静态资产**：评分由官方真实数据预先计算成 JSON，随站点一起发布，运行时只读，不需要实时模拟生成。
- **没有需要共享/持久化的状态**：无账号、无云端存档、无服务器排行榜；"我的结果"通过分享链接参数随身携带。
- 后端的唯一价值（好友 PK 排行榜、云端存档、统一更新、防作弊）全部留到玩法验证之后；届时静态站点加一个轻量 API 即可平滑升级，不需要推翻重做。

## 7. MVP 范围与验收标准

### 7.1 MVP 功能

1. 双模式：经典模式为 MVP 必需；全明星模式后置为迭代项；
2. 组队：先选战队 → 在该战队全历史选手池选 5 人（位置校验），可保存阵容（localStorage）；
3. 战场选择：≥ 3 个代表性赛季（建议 2019 春、2021 秋、2026 夏），决定对手阵容与赛制；
4. 初始阵容：选队后自动加载该队 2026 首发（数据驱动，不维护手写预设清单），可自由调换；
5. 赛季模拟：完整赛季（真实赛制：S/A/B 分组循环、卡位赛、季后赛单败/双败淘汰、决赛），赛制由该赛季 `formats.json` 驱动，支持系列赛间隙换人，每小局生成一段模板化文字战报；输出每轮比分 + 冠军 + 关键战事件；
6. 结算分享：战绩长图 + 可分享链接（打开即还原）。

### 7.2 MVP 验收标准

| 维度 | 标准 |
|---|---|
| 打开速度 | 4G 下首屏 < 2 s，可交互 < 3 s（DevTools 移动模拟验证） |
| 数据正确性 | 抽样 3 个赛季，官方决赛冠军与比分一致率 ≥ 95% |
| 平衡性 | 模拟 100 次：赛季胜率前 30% 的战队夺冠概率 > 50%；常规赛最强队夺冠率 20%–40%（避免确定性） |
| 爆冷能力 | 实力差 1 档的阵容，系列赛爆冷率约 25%–35%（参数可调） |
| 分享 | 战绩图可在微信内长按保存；分享链接在手机浏览器打开即还原阵容 |
| 稳定性 | 引擎可复现（同一 seed 同一结果）；无 console 报错 |

### 7.3 非 MVP（后续迭代）

- 全明星模式细节完善；
- 选手特质（大心脏、英雄勺）增强叙事；
- 社区评分/投票、服务器排行榜、好友 PK 房间；
- 多赛季连续经营模式（转会、阵容演进）。
- 2016–2018 数据补齐（已拍板不做，若未来有需要再评估）。

## 9. 风险与对策

1. **版权/肖像风险**：真实选手名、队名、荣誉用于公开传播有风险。
   - 对策：MVP 定位个人/小圈子传播，页面标注"非官方、民间评分"；若要大规模公开，评估脱敏（化名）或授权。
2. **平衡性崩坏**：全巅峰冠军阵容无脑碾压会毁掉整活乐趣。
   - 对策：爆冷/噪声参数可调；发布前跑 1000 次模拟分布校验。
3. **数据质量**：当前名、位置漂移、比分不一致。
   - 对策：校验门禁 + 用 kpl.qq.com 赛季表做主键关联。
4. **手机性能**：数据包过大、渲染卡顿。
   - 对策：数据分片懒加载 + 性能预算 + 长列表虚拟滚动（如有）。
5. **分享链接失效**：URL 参数过长、编码问题。
   - 对策：选手用短 ID、URL 压缩参数；必要时短链服务（后续）。

## 10. 待拍板决策

1. **选手池范围**：先全量入库、UI 默认展示精选（兼容两种，不阻塞）；是否需要"精选榜"待定。
2. **全明星模式细节**：MVP 后置，需确定组队规则与"第 17 队"的赛制处理。
3. **分享形态**：MVP 纯前端"战绩图 + 链接"基本确认；服务器好友 PK 排行榜后置。
