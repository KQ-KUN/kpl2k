# KPL 版「弗一把」项目评估与实施规划

> 评估日期：2026-08-29
> 评估对象：当前工作区 `KPL弗一把`、本地 `KPL 2K` 数据与工具、CS/电竞类「弗一把」网站
> 结论等级：**建议立项，但先做单机静态 MVP，不直接复制 CS 项目的全栈与多人系统**
> 已确认决策：沿用 `KPL 2K` 红蓝视觉家族、启用已有选手照片并可靠降级、按姊妹站设计双向互通；其余范围按本报告执行。

## 1. 执行结论

这款产品可做，核心风险不在玩法或前端，而在数据口径、选手身份去重、历史战队归属和素材授权。

推荐的第一版是一款移动端优先、无需登录、打开即玩的 KPL 职业选手猜谜网页：每天一题与无限练习并存，玩家最多猜 8 次；每次猜测返回位置、最近战队、首秀年份、最近登场年份、正式赛事数、冠军数和现役状态等结构化反馈。数据由 `KPL 2K` 的处理结果离线生成，游戏运行时只读取一份精简 JSON，进度和战绩只保存在浏览器本地。视觉继承 `KPL 2K` 的红蓝对阵语言，选手照片复用同源 `player_icon` 并提供文字头像降级；两个项目以“姊妹站”方式独立部署、双向导航、共享数据版本和稳定选手 ID。

不建议第一版实现账号、排行榜、经验值、实时匹配、主播房、Redis、PostgreSQL、管理后台或用户自定义头像。这些能力在成熟 CS 项目中成立，但不是验证 KPL 版核心乐趣所必需，并会把一个可静态部署的小项目变成需要长期运维的在线服务。

### 1.1 综合评估

| 维度 | 评分 | 判断 |
|---|---:|---|
| 玩法可理解性 | 9/10 | 规则成熟，单局约 2–5 分钟，失败猜测也能产生信息 |
| KPL 适配度 | 8/10 | 战队、分路、履历和冠军天然适合做比较列 |
| 数据可行性 | 8/10 | `KPL 2K` 已有足够数据，但必须重新按“人”聚合 |
| MVP 技术难度 | 3/10 | 静态前端即可，不需要服务端 |
| 长期维护成本 | 6/10 | 转会、位置漂移、同名选手和新赛事需要持续校验 |
| 权利与合规风险 | 6/10 | 选手照片可从现有数据复用，但来源可用不等于已取得再分发授权；应保留来源说明、失败降级与商业化前授权复核 |
| 商业确定性 | 4/10 | 同类玩法证明形式可行，但目前没有 KPL 版真实留存和分享数据 |

## 2. 「弗一把」是什么

### 2.1 核心原理

「弗一把」是职业选手版的属性推理游戏，基本结构来自 Wordle 类玩法：

1. 系统从题库中选择一名隐藏选手。
2. 玩家输入一名候选选手。
3. 系统逐字段比较候选与答案，并返回颜色、集合重合或数值方向。
4. 玩家利用反馈缩小范围，通常在 8 次内猜中。

CS 开源项目把比较字段设置为国家/地区、赛区、队伍、年龄、位置、Major 冠军数、Major 出场数和现役状态，使用绿色表示完全相同、黄色表示接近、箭头表示目标数值更高或更低，并限制为 8 次机会。[csgofriberg 项目说明](https://github.com/shnlfriberg/csgofriberg#%E7%8E%A9%E6%B3%95)

这里真正值得复用的是三点：

- 每一次错误猜测都提供下一步决策信息。
- 玩家调用的是对职业选手的长期记忆，不是局内操作能力。
- 结果天然适合用无答案的色块矩阵分享。

### 2.2 常见扩展

成熟站点通常在经典模式之外增加每日挑战、无限模式、难度池、连胜、职业轨迹、真假题、同队判断、数据高低、多人竞速和主播房。6657 弗一把目前展示了每日三题、七种自由玩法、生存竞速、12 秒抢答以及最多 24 人的主播房；但这些应理解为成熟期内容，不应整体进入首版。[6657 弗一把](https://www.6657friberg.com/)

其他同类产品还证明了两个值得保留的模式：每日题让所有人共享同一道答案，形成讨论与连续签到；无限模式负责练习和长时游玩。LoLdle 类产品还会在若干次失败后逐步解锁额外提示，并提供色弱模式。[LoLdle Unlimited 玩法说明](https://loldle-unlimited.pages.dev/) [CS Daily Game](https://csdailygame.com/guess)

## 3. 现有 UI 与网站评估

### 3.1 6657 弗一把

实际页面采用近黑底色、荧光黄绿主按钮、白色大标题和大圆角卡片。首页层级是：品牌与 XP → 核心入口 → 今日挑战 → 到访奖励 → 在线对战 → 自由玩法 → 数据与许可。进入经典模式后，页面收敛为返回按钮、模式标题、输入框、确认按钮、剩余次数、属性表头和颜色图例。

优点：

- 核心按钮很醒目，用户能直接进入游戏。
- 规则图例与棋盘同屏，降低首次理解成本。
- 每日、自由、对战三种动机都有清晰入口。
- 页面明确展示数据来源、更新时间和非官方关系。

不宜照搬的部分：

- 首屏功能较多，XP、支持入口、每日奖励和多个玩法同时争夺注意力。
- 多个在线模式要求服务端、房间状态、断线恢复和反作弊。
- 横向属性表在手机上容易过宽，KPL 中文字段比 CS 英文缩写更占空间。
- 荧光黄绿和 BLAST 风格辨识度很高，KPL 版应建立自己的视觉语言。

### 3.2 csgofriberg 开源项目

项目已经包含单人、实时多人、战绩回放、排行榜、匿名访客、登录、多语言、双主题、管理后台和数据导入；技术栈为 React、Vite、Express、Socket.IO、PostgreSQL 与 Redis。[项目功能与技术栈](https://github.com/shnlfriberg/csgofriberg#%E5%8A%9F%E8%83%BD%E7%89%B9%E6%80%A7)

它适合研究领域模型和多人状态机，但不适合作为首版基座：

- 架构规模远大于 KPL 单人猜谜所需。
- 源码采用 AGPL-3.0。若直接修改并通过网络向用户提供服务，许可证要求向远程用户提供对应源码。[AGPL 第 13 条](https://github.com/shnlfriberg/csgofriberg/blob/main/LICENSE#L523-L533)
- KPL 题库、比较字段、名字消歧和移动布局都需要重做，直接 fork 并不能省掉主要工作。

**建议：复用玩法思想和公开交互模式，不复制源码或视觉资产。**

### 3.3 建议的 KPL 视觉方向

不做 BLAST 荧光绿复刻。采用与 `KPL 2K` 同族的“红蓝对阵夜场数据板”：

- 基底沿用深海军蓝：`#0b1a2e` 背景、`#12243f` 卡片、`#e9f1fb` 主文字。
- 品牌首屏或顶部氛围使用红蓝分场渐变：红方 `#c22a2a → #8f1d1d`，蓝方 `#1e3a8a → #1d4ed8`；不把整页每张卡都涂成红蓝。
- 暖金 `#f0b90b` 仅用于主按钮、当前模式和焦点状态，形成与 `KPL 2K` 一致的第三强调色。
- 完全匹配：绿色 + `✓`；部分匹配：琥珀色 + `≈`；不匹配：深灰 + `×`；数值方向附 `↑/↓`。
- 红蓝只表达品牌、对阵和姊妹站归属，不表达“猜对/猜错”，避免红色同时承担阵营与错误两种含义。
- 队伍以文字简称和自绘中性徽章占位，首版不依赖官方队标。
- 选手照片用于候选列表、已提交行和答案卡，不用于提前暴露隐藏答案；加载失败显示昵称首字。
- 字段含义不能只靠颜色表达，必须同时显示图标、文字或纹理，支持色弱用户。
- 动画只做 180–260ms 的逐格翻牌和结果出现，遵循 `prefers-reduced-motion`。

## 4. KPL 版玩法设计

### 4.1 核心规则

- 每局隐藏 1 名选手，最多 8 次猜测。
- 输入框支持中文、英文大小写不敏感、别名和前缀搜索。
- 同名选手必须显示“昵称 + 主要战队 + 活跃年份”供用户消歧，答案实体始终使用稳定 `player_id`。
- 每个猜测只能提交题库中存在的选手。
- 猜中立即结束；8 次用完显示答案、关键履历和再来一局入口。
- 每日模式按北京时间日期和 `data_version` 生成全站一致答案。
- 无限模式每局随机，但同一局在刷新后可恢复。

### 4.2 推荐的反馈列

| 列 | 展示值 | 比较规则 | 数据来源 | MVP 决策 |
|---|---|---|---|---|
| 位置 | 对抗路/打野/中路/发育路/游走，可多选 | 集合完全一致为绿；有交集为黄；无交集为灰 | 赛季统计 + 人工覆盖 | 保留 |
| 最近战队 | 最近一次正式赛事归属 | 相同 franchise 为绿；职业生涯战队有交集为黄；否则灰 | 赛季统计 + `franchises.json` | 保留 |
| 首秀年 | 首个有效正式赛事年份 | 相同为绿；否则箭头指向答案更早/更晚 | 赛季元数据 | 保留 |
| 最近登场 | 最后有效正式赛事年份 | 相同为绿；否则箭头 | 赛季元数据 | 保留 |
| 正式赛事 | 有效主赛事数量 | 相同为绿；否则箭头 | 去重后的 `season_id` | 保留 |
| 冠军数 | 选手在冠军队中有有效出场的赛事数 | 相同为绿；否则箭头 | 赛季冠军 + 当季归属 | 保留，但需人工抽查 |
| 现役 | 最近一次有效记录是否在当前赛季窗口 | 相同为绿；否则灰 | 当前赛季白名单 | 保留，页面解释口径 |
| 巅峰评分 | KPL 2K 的最高年度评分 | 相同为绿；否则箭头 | 民间评分模型 | 默认隐藏，仅可作为进阶模式 |
| 总局数 | 有效正式赛事累计小局 | 相同为绿；否则箭头 | 赛季统计 | 第 5 次失败后的补充提示 |

不建议首版加入：

- 年龄/出生年：`KPL 2K` 当前没有稳定字段，逐人补录维护成本过高。
- 国籍/地区：KPL 选手区分度低，且现有数据不完整。
- 常用英雄：版本变化太强，多赛季集合会趋同，作为经典列信息质量不足。
- KDA、胜率或巅峰评分作为主列：普通玩家难以记忆精确数值，且评分含人工校准，不应伪装成官方事实。

选手照片不作为比较字段，但纳入展示层。自动补全只加载当前可见候选；已提交后才在猜测行显示照片；答案揭晓后在结算卡显示大图。任何图片失败都必须无闪烁地退回昵称首字，不能阻塞提交与结算。

### 4.3 难度池

三个池应嵌套，猜测搜索范围可以比目标池更宽：

| 难度 | 初始生成标准 | 当前快照规模 | 后续维护 |
|---|---|---:|---|
| 热门 | ≥5 个正式赛事、≥100 局、巅峰评分 ≥80，再人工增删 | 150 名自动候选 | 每赛季人工审一次，目标约 100–150 人 |
| 常规 | ≥3 个正式赛事且 ≥50 局 | 281 名 | 自动生成 + 错误名单 |
| 硬核 | 任一正式赛事已知位置且 ≥5 局 | 591 名 | 自动生成；默认不作为新手每日题 |

难度不能只由评分决定。热门程度还受冠军、现役、人气和传播记忆影响，因此保留小型人工白名单/黑名单，而不是建立复杂的“人气算法”。

### 4.4 逐步提示

- 第 1–4 次：只显示 7 个基础反馈列。
- 第 5 次失败：解锁累计小局数方向。
- 第 7 次失败：显示答案的一个职业生涯战队简称，但不显示年份。
- 第 8 次失败：揭晓答案。

这一设计能解决少数属性指纹相同的问题。按当前数据审计，591 名可用选手用 7 个基础属性形成 576 个不同指纹，13 组、共 28 名选手存在属性完全相同的碰撞；加入累计小局数后，本次快照中碰撞归零。累计局数会随数据更新变化，所以只作为后期提示，不应成为日常记忆题的第一列。

### 5.2 可以直接借鉴

1. **稳定选手 ID。** `player_id` 应成为答案和猜测的唯一标识，昵称只用于显示和搜索。
2. **赛季分片和数据版本。** 沿用 `schema_version`、`data_version`，让每日题在数据更新后可追溯。
3. **历史战队 franchise。** 同一个俱乐部改名后仍按同一 franchise 比较，避免 QGhappy/重庆狼队被当成无关队伍。
4. **位置与战队人工覆盖。** 当前清洗脚本会在输出前应用 `player_versions.json` 中的位置、战队和评分修正，这部分必须进入猜谜数据生成流程。
5. **正式战场标记。** 使用 `is_battlefield` 排除选拔赛、季前赛等噪声赛事。
6. **构建与验证思路。** 复用“原始数据 → 清洗 → 派生 JSON → 静态验证”的流水线，不在浏览器中临时推导复杂履历。
7. **移动端选手搜索经验。** 现有选手库已验证卡片、筛选、搜索和深色主题，但猜谜页需要更紧凑的提交列表。
8. **照片字段与降级实现。** `players.json` 的 `player_icon` 已被选手库和模拟器使用，现有 UI 在图片加载失败时会回退到文字头像；KPL 弗一把沿用字段和交互思路，不复制生成页面代码。
9. **家族视觉。** `KPL 2K` 首页已经使用红蓝分场渐变、深海军蓝底色与金色焦点，适合作为姊妹站设计令牌来源。

### 5.3 不能直接拿来当题库

1. **选手库按“人 × 战队”建卡。** `player_library.json` 有 701 张卡，但只有 448 个不同的基础 `player_id`；例如久酷会因多个战队产生多张卡。猜谜目标必须按人聚合，否则同一个昵称可能对应多个答案。
2. **主档存在同名不同人。** 当前有 8 组重复昵称、涉及 17 个不同 `player_id`，其中 `KK` 有 3 人。搜索结果必须显示战队与年代，禁止只按昵称提交。
3. **低样本与未知位置。** 3,290 条赛季记录中有 352 条少于 5 局，33 条位置为“未知”。首版应排除而不是猜测补齐。
4. **历史字段会受当前值污染。** KPL 2K 已为部分选手维护人工修正，但并不代表所有历史记录都已人工穷尽。
5. **现役不是永久事实。** 现役口径必须基于“数据快照中的当前赛季窗口”，并在页面显示更新时间。
6. **头像 URL 有混合协议与授权风险。** 647 条非空 URL 中有 78 条仍为 HTTP，在 HTTPS 站点会被浏览器拦截；其余远程资源也可能失效。首版可在 `<img>` 中引用可用 HTTPS URL，并设置固定尺寸、懒加载与异步解码，但不批量下载、打包或转售，必须保留文字头像降级。若以后需要把照片绘入可下载分享图，再单独解决 CORS、缓存和授权问题。

## 6. 新题库的数据契约

建议在本项目内建立独立导入脚本，读取任意 `--source` 指向的 KPL 2K 数据目录，不硬编码本机绝对路径。生成结果提交到当前仓库，线上运行不依赖兄弟目录。

```json
{
  "schemaVersion": 1,
  "dataVersion": "2026-08-15",
  "sourceCommit": "c4ecd2e",
  "generatedAt": "2026-08-29T00:00:00+08:00",
  "players": [
    {
      "id": "81AEA3A32BA205D61F400FA612808490",
      "nickname": "Fly",
      "aliases": ["fly"],
      "iconUrl": "https://example.invalid/player.png",
      "positions": ["对抗路"],
      "latestTeamId": "10006",
      "latestTeamName": "武汉eStarPro",
      "teamHistory": ["10001", "10018", "10006"],
      "debutYear": 2019,
      "latestYear": 2026,
      "eventCount": 27,
      "championshipCount": 4,
      "totalGames": 1233,
      "peakRating": 97.5,
      "active": true,
      "difficulty": ["popular", "normal", "hardcore"]
    }
  ]
}
```

注意：上例只演示契约结构，具体归属与统计必须由生成器重新计算并经审计文件验证，不能把报告示例当成手工真值。

### 6.1 生成规则

1. 先应用 KPL 2K 的位置和战队覆盖。
2. 只纳入 `is_battlefield = true` 的赛事。
3. 单条赛季记录要求 `games >= 5` 且位置非“未知”。
4. 按 `player_id` 聚合，不按昵称或战队聚合。
5. `latestTeam` 取结束日期最新的有效赛事归属。
6. `championshipCount` 只在选手当季有有效出场且其 franchise 等于赛季冠军时累计。
7. `active` 由配置中的当前赛季窗口计算，不以“最新年份等于系统年份”写死。
8. 生成 `quiz_data_audit.json`，记录总人数、各难度人数、同名组、未知字段、冠军异常、指纹碰撞和数据版本。
9. `iconUrl` 只保留 HTTPS；空值、HTTP、无效 URL 或加载失败统一使用确定性的文字头像，不影响选手入池。
10. 若审计关键项失败，则构建失败，不发布半更新题库。

### 6.2 数据更新流程

```text
KPL 2K 更新并通过自身校验
  → KPL弗一把运行 import_kpl2k
  → 生成 quiz_players.json + quiz_data_audit.json
  → 人工审热门池、同名和冠军名单
  → 运行游戏逻辑与 UI 测试
  → 发布静态站点
```

每次更新必须保留 `sourceCommit`、`dataVersion` 和题库哈希。每日题种子应包含数据版本，避免同一天因热更新在不同设备出现不同答案。

### 7.1 MVP 必做

- 每日一题。
- 无限练习。

### 9.3 核心接口

```ts
type Feedback = "exact" | "partial" | "miss" | "higher" | "lower";

interface GuessResult {
  playerId: string;
  position: Feedback;
  latestTeam: Feedback;
  debutYear: Feedback;
  latestYear: Feedback;
  eventCount: Feedback;
  championshipCount: Feedback;
  active: Feedback;
}

function comparePlayers(guess: QuizPlayer, target: QuizPlayer): GuessResult;
```

比较引擎必须是无副作用纯函数。UI 不自行判断颜色，所有模式共用同一套比较规则和测试。

### 9.4 每日题与防作弊

静态站点无法真正隐藏答案，懂开发者工具的用户可以读取题库或推导每日种子。MVP 接受这一点，因为没有奖金或可信排行榜。每日题使用稳定 PRNG：

```text
seed = SHA-256("Asia/Shanghai 日期|难度|dataVersion|规则版本")
targetIndex = seededRandom(seed) % pool.length
```

若后续加入排名、奖励或正式赛事，答案选择和提交校验必须迁移到服务端，不能继续相信客户端结果。

### 9.5 本地存储

只保存：设置、当前局、每日完成记录和聚合战绩。每个对象带 `storageVersion`，解析失败时只重置对应键，不清空整个站点存储。无需保存姓名、邮箱、设备指纹或其他个人信息。

### 9.6 姊妹站互通契约

两个项目保持独立仓库、独立构建、独立部署。`KPL 弗一把` 在构建期消费 `KPL 2K` 的数据快照，运行期不请求 `KPL 2K` 的接口或静态 JSON；任一站点短暂不可用时，另一个站点仍能完整运行。首版不抽取共享 npm 包或公共后端，等出现第三个消费者或重复维护已经造成实际错误时再评估独立数据包。

| 互通层 | MVP 契约 | 说明 |
|---|---|---|
| 品牌 | 共同使用深海军蓝基底、红蓝分场、金色焦点；显示“`KPL 2K` 姊妹站” | 建立家族感，但各自保留游戏结构和名称 |
| 导航 | 弗一把上线即链接到现有 `KPL 2K`；新站获得稳定生产 URL 后，再在 `KPL 2K` 增加返回链接 | 不写死尚不存在的域名，不形成发布死链 |
| 数据 | 保留同一 `player_id`、`dataVersion`、`sourceCommit`，导入结果附题库哈希 | 两站对同一选手可追溯到同一数据快照 |
| 选手深链 | 预留 `KPL 2K/player_library.html?player=<player_id>` | 当前选手库尚未解析该参数，需在双向互链阶段补最小定位逻辑 |
| 弗一把 → 2K | 结算后提供“去 KPL 2K 看履历/组阵容”，携带已揭晓的 `player_id` | 只在答案揭晓后生成，避免泄题 |
| 2K → 弗一把 | 首页/选手库提供“去姊妹站猜选手”的普通入口 | MVP 不携带目标选手，避免把答案写进 URL |
| 用户状态 | 各自使用独立 `localStorage`，不跨域同步战绩或设置 | 不增加账号、Cookie、OAuth 和跨域隐私负担 |

现有 `KPL 2K` 生产入口按 `https://kpl2k-kpl2k-d0gigrx6e89914f65.webapps.tcloudbase.com` 接入。正式修改对方站点前先确定 KPL Guessing 的稳定生产 URL，再一次性补齐反向导航、选手深链、断链检查和两个站点的版本说明。

## 10. 验收与测试

### 10.1 数据门禁

- 所有答案 `player_id` 唯一。
- 昵称为空、位置未知、无有效赛事的选手不能进入目标池。
- 同名组全部具备可显示的消歧信息。
- 三个难度池嵌套，人数符合配置范围。
- 每名选手的首秀年 ≤ 最近登场年。
- 冠军数 ≤ 正式赛事数。
- 最近战队必须存在于 franchise 映射。
- 当前赛季窗口必须来自配置，不能依赖系统年份猜测。
- 审计报告与生成 JSON 的哈希匹配。

### 10.2 逻辑测试

- 相同位置集合返回 `exact`，部分交集返回 `partial`。
- 最近战队相同为 `exact`，仅历史交集为 `partial`。
- 数值箭头方向以答案为参照，所有列一致。
- 重复猜测不能消耗次数。
- 第 5、7 次提示只解锁一次。
- 同一日期、难度、数据版本在不同时区设备上都按北京时间得到同一答案。
- 数据版本变化时旧局得到明确迁移或失效提示。

### 10.3 UI 与可用性

- 360×800、390×844、768×1024、1440×900 四档视觉检查。
- 手机键盘弹起时仍可看到输入区和候选列表。
- 全流程可只用键盘完成。
- 色块在灰度或色弱模式下仍能区分。
- 弱网或离线重开已缓存页面时，当前局不丢失。
- 题库加载失败显示重试，不出现空白页。
- 照片空值、HTTP、404 和慢加载时使用文字头像，不能造成布局跳动或功能阻塞。
- 分享文本不泄露答案。
- 两站导航在生产环境无死链；未揭晓答案前页面和 URL 不包含目标 `player_id`。

### 10.4 MVP 完成标准

1. 新用户不看长说明也能在 30 秒内完成第一次提交。
2. 从进入页面到可输入不超过 2 秒，目标设备上无明显布局跳动。
3. 591 名硬核候选通过数据门禁；热门池逐人抽查。
4. 20 个预设对局的比较结果全部正确。
5. 每日题跨刷新、跨浏览器时区测试一致。
6. 手机端 8 次猜测完整可读，不依赖横向滚动。
7. 发布页明确标注非官方、数据版本和纠错入口。

## 11. 实施里程碑

### M0：题库生成与口径冻结（1–2 天）

交付：导入脚本、题库契约、审计报告、热门候选清单。

验收：591 名基础候选可重复生成；同名、冠军、位置和当前赛季口径已列出；相同输入生成完全相同输出。

### M1：核心纵切（3–5 天）

交付：单个难度的无限模式、带照片降级的搜索与消歧、8 次猜测、比较棋盘、胜负结算、最小逻辑测试。

验收：从打开到完成一局全链路可用，桌面和手机真实浏览器通过。

### M2：每日、难度与分享（2–3 天）

交付：每日题、三个难度、逐步提示、本地统计、分享色块、数据说明。

验收：北京时间确定性、刷新恢复、分享不泄题、存储版本迁移通过。

### M3：视觉与发布门禁（2–4 天）

交付：红蓝姊妹站视觉、完整响应式样式、色弱/减少动画、错误状态、静态部署、正向站点链接和发布检查脚本；新站 URL 稳定后在 `KPL 2K` 补反向入口与选手深链。

验收：四档视口截图审查、生产构建、静态资源路径、缓存更新和线上真实交互通过。

### M4：小范围验证（至少 7 天自然观察）

邀请 KPL 重度、普通和回流观众各若干人，不先做多人功能。记录：

- 首局完成率。
- 平均猜测次数与失败率。
- 每个难度的选择比例。
- 次日与 7 日再次打开比例。
- 分享按钮使用率。
- 每 100 局的数据纠错数量。
- 玩家抱怨是“答案太偏”还是“反馈不可信”。

进入 P1 的建议阈值：首局完成率 ≥70%，热门难度失败率 20%–55%，每 100 局严重数据错误 <1，且有明确的重复游玩或分享行为。阈值是产品假设，不是现有事实，可在首轮测试后调整。

## 12. 风险与对策

### 12.1 数据正确性

最高风险。错误战队或冠军反馈会直接破坏推理链，玩家一次发现错误就会怀疑整局。

对策：使用稳定 ID；过滤低样本；显式应用覆盖表；热门池逐人审；生成审计报告；页面提供带 `player_id` 和数据版本的纠错链接。

### 12.2 数据与素材权利

中国著作权法明确保护计算机软件、美术、摄影等作品及信息网络传播权；腾讯法律声明也保留其作品和品牌内容的权利。[中国人大网《著作权法》](https://www.npc.gov.cn/c2/c30834/202011/t20201119_308796.html) [腾讯法律声明](https://www.tencent.net.cn/zh-cn/legal-statement/)

降低风险的首版策略：

- 只展示必要的选手昵称、文字战队简称和自行计算的事实性汇总。
- 不复制 CS 站点代码、图标、配色或品牌素材。
- 不使用官方 KPL Logo、俱乐部 Logo 和比赛截图；选手照片只引用数据源现有 HTTPS URL，并提供文字降级，不批量下载、打包或宣称获得官方授权。
- 页面写明“非官方粉丝项目，与腾讯、王者荣耀职业联赛及各俱乐部无隶属或授权关系”。
- 展示数据更新时间、处理口径和纠错方式，不宣称“官方完整数据库”。
- 若要商业化、投广告、接赞助或大量使用品牌素材，发布前单独做授权与法律评估。

本节是产品风险控制建议，不替代专业法律意见。

### 12.3 静态站作弊

对休闲每日题影响有限；对排行榜和奖励不可接受。首版不做可信排名，后续只有在确有需求时增加最小服务端。

### 12.4 题库太难

591 人全部开放会让普通用户感到随机。默认难度必须是热门，硬核只给主动选择的用户；失败后给逐步提示，不用无限加次数。

### 12.5 赛季更新导致口径漂移

新转会会改变最近战队和现役状态。通过数据版本、来源提交、规则版本和每日种子绑定，保证每次发布可追溯；不要运行时直连官方接口。

## 13. 最终建议

1. **立项。** 核心玩法与 KPL 数据高度匹配，现有数据足以完成首版。
2. **独立实现。** 借鉴 CS 版交互，不 fork 其全栈代码；避免 AGPL 和不必要的运维复杂度。
3. **先做数据。** 第一项开发工作不是画首页，而是生成按 `player_id` 去重、可审计的 `quiz_players.json`。
4. **默认热门。** 首版以约 100–150 名高认知选手验证乐趣，常规和硬核作为主动选项。
5. **照片渐进增强。** 展示现有 HTTPS 选手照片，但玩法、布局和分享不能依赖照片成功加载；HTTP 与缺图一律降级。
6. **姊妹站而非耦合站。** 先做共享视觉令牌、构建期数据契约、双向导航和答案揭晓后的选手深链，不做运行时跨站依赖。
7. **单页优先。** 打开即猜，先完成“搜索 → 提交 → 反馈 → 推理 → 结算 → 分享”闭环。
8. **多人后置。** 只有单人模式出现真实留存和同时在线需求后，才引入服务端与房间系统。
